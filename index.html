How it works

From finding to merged fix, without the guesswork

Scanners are good at telling you what's wrong. VRA+ does the next part: it changes the code, proves the change is safe, and delivers it for review.

  1. 01

    Scan

    Trivy, Semgrep and Checkov run together; findings are normalised, de-duplicated and grouped by type — SCA, SAST, IaC, secrets.

    vra scan
  2. 02

    Fix

    Each finding with a known, rule-based fix is applied in an isolated git worktree — one change at a time, most severe first.

    vra remediate --apply
  3. 03

    Prove

    Your build, your tests and a docker build of every Dockerfile must still pass, and a re-scan must show the finding gone.

    build · test · re-scan
  4. 04

    Deliver

    Verified fixes land in one pull or merge request. Anything that breaks the build becomes a draft with the change applied and the failure output.

    vra remediate --open-pr

What it fixes

Real fixes, not just a longer report

Every fix comes from a deterministic source — a scanner advisory, a rule's own fix, or a built-in hardening recipe. No model guessing at your code.

Vulnerable dependencies

Upgrades each package to the lowest version that closes every CVE, respecting backport release lines. Direct and transitive — via overrides, constraints and dependency management. Lockfiles are refreshed; formatting and line endings are kept. Major upgrades are flagged for review.

  • Maven
  • Gradle
  • npm
  • yarn
  • pnpm
  • pip
  • uv
  • Poetry
  • Go modules

Insecure code

Applies the fix that ships with the Semgrep rule — e.g. shell=True → shell=False. Refused if the file changed since the scan, and always marked for review.

Dockerfiles

Built-in hardening, each verified with a real image build:

  • run as a non-root user
  • pin base images to a digest
  • COPY instead of ADD
  • no SSH port 22
  • merge apt-get update with install
  • MAINTAINER → LABEL

CI supply chain

Pins third-party pipeline steps from a mutable tag to their full commit SHA — @v4 becomes @11d5960a… # v4 — so a moved tag can't change what your pipeline runs.

Hardcoded secrets

A committed secret must be revoked, not deleted. VRA+ opens one issue per repository with every location and the revoke → move → purge-history steps. Values are never copied.

Findings without a deterministic fix are listed too — nothing silently disappears.

Verification

A fix that breaks the build isn't a fix

Before touching anything, VRA+ runs every check on your untouched code. Then each fix has to pass all of them again.

  • Everything it touches is checked. A dependency bump must pass your tests and still build your Docker image — requests 2.33 passes on a modern Python but breaks a python:3.9 image. VRA+ catches that.
  • One change at a time. A failure is pinned to the change that caused it and never blocks the fixes that work.
  • No silent downgrades. A transitive pin that would undercut a related upgrade is skipped.
  • Your working tree is never touched. All work happens in a temporary git worktree; results land on branches.
  • Missing toolchain ≠ success. No mvn or docker on the machine? The fix is marked unverified and the PR says so.

CI/CD

Just the CLI. No plugin, no app to install.

Two stages: scan publishes the report, remediate picks it up on the same commit and opens the fix PR/MR. A weekly schedule keeps it current; merging it re-runs the scan.

  • GitHub Actions, GitLab CI, Jenkins — anything that runs a shell
  • Fail on CRITICAL, allow HIGH, or report-only with --no-fail
  • Configure with YAML, environment variables or flags

How the two stages work, tokens and toolchains →

.github/workflows/vra.yml

name: VRA+

on:
  schedule:
    - cron: "0 6 * * 1"            # weekly: new CVEs appear against unchanged code
  push:
    branches: [main]               # e.g. after a VRA+ PR is merged
  workflow_dispatch:

env:
  VRA_URL: https://github.com/gboie/vra-plus/releases/latest/download/vra-linux-amd64

jobs:
  # ── Stage 1: scan, and publish the report ──────────────────────────
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: Install VRA+
        run: curl -fsSLo vra "$VRA_URL" && chmod +x vra && sudo mv vra /usr/local/bin/

      - name: Scan
        run: vra scan --no-fail .

      - name: Publish the scan report
        uses: actions/upload-artifact@v4
        with:
          name: vra-scan-report
          path: vra-reports/scan-report.json
          retention-days: 7

  # ── Stage 2: fix what stage 1 found ────────────────────────────────
  remediate:
    needs: scan
    runs-on: ubuntu-latest
    permissions:
      contents: write              # push the vra/* branches
      pull-requests: write         # open / update the PRs
      issues: write                # the secrets issue
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.sha }}   # exactly the commit that was scanned
          fetch-depth: 0
          token: ${{ secrets.VRA_TOKEN }}

      # Your build toolchain, so every fix is verified by your build and tests:
      - uses: actions/setup-node@v4
        with: { node-version: "20" }

      - name: Install VRA+
        run: curl -fsSLo vra "$VRA_URL" && chmod +x vra && sudo mv vra /usr/local/bin/

      - name: Get the scan report from stage 1
        uses: actions/download-artifact@v4
        with:
          name: vra-scan-report
          path: vra-reports

      - name: Remediate and open the PR
        env:
          # A personal or app token: PRs opened with the default GITHUB_TOKEN
          # don't trigger your CI. Needs Contents, Pull requests, Issues and
          # Workflows: Read and write.
          GITHUB_TOKEN: ${{ secrets.VRA_TOKEN }}
        # Exit code 2 = some fixes need a human (draft PRs opened): not a failure.
        run: vra remediate --open-pr --report vra-reports/scan-report.json || [ $? -eq 2 ]

.gitlab-ci.yml

stages: [scan, remediate]

variables:
  VRA_URL: https://github.com/gboie/vra-plus/releases/latest/download/vra-linux-amd64

.vra:
  image: python:3.12               # an image with your build toolchain
  before_script:
    - curl -fsSLo /usr/local/bin/vra "$VRA_URL" && chmod +x /usr/local/bin/vra
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"           # weekly schedule
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH     # e.g. after a VRA+ MR is merged

# ── Stage 1: scan, and publish the report ────────────────────────────
vra-scan:
  extends: .vra
  stage: scan
  script:
    - vra scan --no-fail .
  artifacts:
    paths: [vra-reports/scan-report.json]
    expire_in: 7 days

# ── Stage 2: fix what stage 1 found ──────────────────────────────────
vra-remediate:
  extends: .vra
  stage: remediate
  needs: [vra-scan]                # same commit; downloads the scan report
  variables:
    GIT_DEPTH: 0                   # full history to branch from
  script:
    # GITLAB_TOKEN: a masked CI/CD variable holding a project access token
    # with the api + write_repository scopes (CI_JOB_TOKEN can't open MRs).
    - git remote set-url origin "https://oauth2:${GITLAB_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.git"
    # Exit code 2 = some fixes need a human (draft MRs opened): not a failure.
    - vra remediate --open-pr --report vra-reports/scan-report.json || [ $? -eq 2 ]
