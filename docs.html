Step 1 · Connect to GitHub or GitLab

Do this first. vra scan and vra remediate --apply work on any clone and need no account. For vra remediate --open-pr to open pull requests (GitHub) or merge requests (GitLab), VRA+ talks to your git host. The push always uses your own git credentials (SSH key or HTTPS login); a token is only used for the API.

GitHubGitLab
With a tokenOpens and updates the PR, a draft per fix that needs a human, and the secrets issue; closes drafts that are no longer neededThe same, for MRs
No token
(your machine)		Pushes the branches and prints a ready-to-click link for each PRThe push opens the MRs (git push options); a link for the secrets issue
In CIToken requiredToken required (CI_JOB_TOKEN can't push or open MRs)
GitHub: create a tokenfine-grained PAT

Already use the GitHub CLI? If gh auth status says you're logged in, skip this: with no token set, VRA+ reuses your gh login (turn it off with github.use_gh_login: false).

  1. Open github.com/settings/personal-access-tokens/new — or your profile picture → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Token name: e.g. vra-plus. Expiration: pick a date (90 days is sensible).
  3. Resource owner: you, or the organization that owns the repository. Organizations can require an admin to approve the token first.
  4. Repository access: Only select repositories, then pick the ones VRA+ will open PRs on.
  5. Permissions → Repository permissions, set the ones in the table below.
  6. Generate token and copy it (starts with github_pat_). GitHub shows it once.
PermissionAccessWhy
Pull requestsRead and writeopen, update and close the PRs
IssuesRead and writesecrets issue and PR labels
MetadataRead-onlyadded automatically
ContentsRead and writeonly if git pushes with this token (HTTPS remote using it, CI)
WorkflowsRead and writeonly if git pushes with this token — a fix can pin actions in .github/workflows/, and GitHub rejects such pushes without it

A classic token also works (github.com/settings/tokens/new, scope repo, plus workflow if git pushes with it), but it reaches every repository you can. GitHub Enterprise Server: same steps on your server, then set github.url: https://<host>/api/v3.

GitLab: create a tokenoptional on your machine

Working on your machine only? You can skip this: without a token, the push opens the MRs (see below). Create one for full MR descriptions, the secrets issue opened for you, or CI.

  1. Open gitlab.com/-/user_settings/personal_access_tokens (self-managed: https://<your-gitlab>/-/user_settings/personal_access_tokens) — or your avatar → Edit profile → Access tokens → Add new token.
  2. Token name: e.g. vra-plus. Expiration date: required (at most a year).
  3. Scopes: api — GitLab has no narrower scope that can create MRs. Add write_repository only if git pushes with this token (HTTPS remote using it, CI).
  4. Create token and copy it (starts with glpat-). GitLab shows it once.

You need at least the Developer role on the project. For CI, prefer a project access token — it acts as a bot, not as you: project → Settings → Access tokens → Add new token, role Developer, scopes api + write_repository. On GitLab.com these need a Premium or Ultimate plan; on self-managed GitLab every tier has them.

Add the token to VRA+env var or user config

An environment variable is best — nothing is written to disk:

# GitHub — any one of these
export GITHUB_TOKEN=github_pat_xxxx
export VRA__GITHUB__TOKEN=github_pat_xxxx

# GitLab — any one of these
export GITLAB_TOKEN=glpat-xxxx
export VRA__GITLAB__TOKEN=glpat-xxxx

Or your user config file, readable only by you:

mkdir -p ~/.config/vra+ && touch ~/.config/vra+/config.yaml && chmod 600 ~/.config/vra+/config.yaml
# ~/.config/vra+/config.yaml
github:
  token: github_pat_xxxx
gitlab:
  token: glpat-xxxx
  url: https://gitlab.com        # self-managed: https://gitlab.company.com

Don't put a token in the repository's vra.yaml — that file is meant to be committed.

Which one wins (first found). GitHub: github.token (config file, overridden by VRA__GITHUB__TOKEN) → GITHUB_TOKEN → GH_TOKEN → your gh login → no-token mode. GitLab: gitlab.token (overridden by VRA__GITLAB__TOKEN) → GITLAB_TOKEN → no-token mode. GitHub or GitLab is picked from the origin remote.

Check it works 
vra --format json config | jq .auth   # where each token comes from — never the token
# { "github": "GITHUB_TOKEN", "gitlab": "none: --open-pr opens MRs through git push options" }

# GitHub: prints the repository name, not "Bad credentials"
curl -s -H "Authorization: Bearer $GITHUB_TOKEN" https://api.github.com/repos/OWNER/REPO | grep full_name

# GitLab: prints the project path (slash encoded as %2F)
curl -s -H "PRIVATE-TOKEN: $GITLAB_TOKEN" "https://gitlab.com/api/v4/projects/GROUP%2FPROJECT" | grep -o '"path_with_namespace":"[^"]*"'
No token on GitLab: the push opens the MRs

VRA+ pushes each branch on its own with git push options, and GitLab creates the MR as the branch arrives — over SSH or HTTPS, with your own credentials:

git push --force -o merge_request.create -o merge_request.target=main \
  -o "merge_request.title=VRA+: fix 10 security findings" \
  -o merge_request.label=security -o merge_request.remove_source_branch \
  origin vra/remediate
  • One MR for vra/remediate, and one draft MR per vra/needs-human/* branch, targeting vra/remediate.
  • Title, target, labels and "delete source branch" are set. Push options can't carry multi-line text, so the description is one line pointing to the full text in vra-reports/pr-<branch>.md — paste it in if you want it on the MR.
  • An issue can't be opened by a push: VRA+ prints a link to GitLab's New issue form, filled in with the secrets issue.
No token on GitHub: one click per PR

GitHub can't open a PR from a push. VRA+ pushes the branches and prints a link per PR that opens GitHub's Open a pull request form with the title and labels filled in. A short description is in the link too; a long one stays in vra-reports/pr-<branch>.md and the form tells you which file to paste.

Several PRs? A run makes at most one main PR plus one draft per fix that needs a human. They're printed numbered, main first:

No GitHub token — pushed 3 branch(es). Open each PR with one click (in this order):
1. vra/remediate → main
   https://github.com/acme/app/compare/main...vra%2Fremediate?expand=1&title=…
2. vra/needs-human/pyjwt → vra/remediate  — choose “Create draft pull request”
   https://github.com/acme/app/compare/vra%2Fremediate...vra%2Fneeds-human%2Fpyjwt?expand=1&title=…
3. vra/needs-human/urllib3 → vra/remediate  — choose “Create draft pull request”
   …
  • Click each link once. Drafts target vra/remediate, so each shows only its own change.
  • The next run force-pushes the same branches, so PRs you've opened update by themselves; only a new vra/needs-human/* branch prints a new link.
  • What a token adds (both hosts): full descriptions kept current, the main PR linking its drafts, drafts closed once their fix passes, the secrets issue opened and updated for you, and CI.

Quick start

The usual flow: scan, preview the fixes, apply them locally, then open a PR/MR.

# 1. Scan with all three bundled scanners (writes vra-reports/scan-report.json)
vra scan .

# 2. Preview the fixes — touches nothing
vra remediate

# 3. Apply and verify each fix on a local branch (vra/remediate)
vra remediate --apply

# 4. Push and open the PR/MR, drafts and secrets issue (token: see Step 1)
vra remediate --open-pr

Command guides

The five commands you'll run most — when you need each one, and exactly what it does.

1 vra scanSee what's vulnerable

When do you need it?

Whenever you need to know your security exposure: on every pull request, before a release, on a schedule for code nobody is changing (new CVEs are published daily against old code), when you inherit a codebase, or when a customer or auditor asks for evidence. It's always the first step — vra remediate works from its report.

What happens, step by step

  1. Picks the scanners. All three by default. A target that isn't a local path is treated as a container image and scanned with Trivy only.
  2. Refreshes what it knows. Trivy downloads the latest vulnerability database and Semgrep fetches the latest registry rules. Air-gapped? Set scanner.update_db / update_rules to false to scan offline with bundled rules.
  3. Runs each scanner on the target. Trivy reads manifests, lockfiles and images; Semgrep reads source code; Checkov reads Terraform, CloudFormation, ARM, Kubernetes manifests, Dockerfiles and secrets, skipping node_modules, build, vendor and similar. Each scanner has a time limit (scanner.timeout_seconds, 300 s).
  4. Normalises the findings into one format — severity, CVE or rule ID, package and fixed version, file and line — keeps those at or above --severity, and groups them by type: SCA, Container, SAST, IaC, Secrets.
  5. Applies the fail policy: counts findings per severity against the --max-* limits.
  6. Writes the report vra-reports/scan-report.json — every finding, whether it has a known fix, and the policy result.

What you get

  • A terminal report grouped by type, coloured by the worst severity in each group
  • vra-reports/scan-report.json for vra remediate, dashboards or scripts
  • Exit code 1 when the policy is breached, 0 otherwise — so a pipeline can block on it

Good to know

  • Read-only. It never changes your code.
  • Needs network access for the database and rule updates, unless you turn them off.
  • A scanner that can't run is shown in the summary — never silently skipped.
vra scan .                               # all three scanners
vra scan --no-fail --severity MEDIUM .   # CI reporting step

2 vra remediatePreview the fixes

When do you need it?

Right after a scan, to answer “how much of this can be fixed automatically, and what exactly would change?” — for sprint planning, estimating the effort left for humans, or reviewing the plan before you let VRA+ touch a repository. It's safe to run anywhere: no build tools, no git changes.

What happens, step by step

  1. Reads the scan report (vra-reports/scan-report.json, or --report). It doesn't re-scan.
  2. Works out a fix for each finding:
    • Dependencies — the lowest version that closes every CVE for that package, respecting release lines; major upgrades are flagged for review.
    • Code — the fix that ships with the Semgrep rule.
    • Dockerfiles and CI workflows — VRA+'s built-in hardening and SHA pinning.
    • Secrets — listed for the rotation issue, never patched.
    • Everything else — listed as manual, so nothing silently disappears.
  3. Applies your filters: --kind, --only, remediation.kinds and remediation.autofix_exclude.
  4. Prints the plan and writes it to vra-reports/remediation-plan.json.

What you get

  • A table of every planned change: package or rule, current → target version, CVEs closed
  • remediation-plan.json for review or tooling
  • Exit code 0

Good to know

  • Changes nothing — no branch, no build, no commit. Only the report folder is written.
  • The plan says what VRA+ will try; --apply is where each fix has to prove it works.
vra remediate
vra remediate --kind dependency   # just the upgrades

3 vra remediate --applyMake and prove the fixes locally

When do you need it?

When you want the fixes made and proven before anyone else sees them: a developer clearing a security backlog, a first trial of VRA+ on a repository, or teams that don't want to give a tool an API token. You get ordinary local branches to review, test and push yourself.

What happens, step by step

  1. Builds the plan from the scan report, exactly like vra remediate.
  2. Makes a separate working copy — a git worktree in a temporary folder on branch vra/remediate, starting from your current commit. Your folder, branch and uncommitted edits are never touched (and aren't included). The branch is recreated on every run.
  3. Checks the untouched code first — your build, your tests and a docker build of each Dockerfile. A check that already fails can't judge a fix: if the main build is broken, that project's fixes go to a human. A missing tool (no mvn, no docker) means unverified, never passed.
  4. Tries each fix, one at a time, most severe first:
    • apply the change (manifest + lockfile, rule fix, Dockerfile, workflow pin),
    • run every check again — build, tests, image builds,
    • re-scan: the CVE must be gone and no new ones added,
    • all good → commit that one change; anything fails → roll back and try the next fixing version (up to 3, --max-candidates).
  5. Retries failed fixes on top of later ones — sometimes upgrade B only works once A is in.
  6. Saves what failed for a human: each fix that never passes gets a branch vra/needs-human/<name>, stacked on vra/remediate, with the failing change committed.
  7. Cleans up the temporary copy. If nothing could be fixed, the empty branch is removed too.

What you get

main                            # your branch — unchanged
 └─ vra/remediate               # one commit per verified fix
     ├─ vra/needs-human/pyjwt   # failing change + details
     └─ vra/needs-human/werkzeug
  • Local branches only — nothing is pushed, no PR is opened
  • remediation-report.json (fixed, skipped, needs a human — and why) and pr-<repo>.md, a ready-made PR description
  • Exit code 0 all applied · 2 some need a human · 1 error

Good to know

  • It runs your project's code — installs, build scripts, tests, docker build — just as CI would.
  • Commits use your git name and email, and skip git hooks (--no-verify).
  • Re-running replaces vra/remediate — move any commits of your own to another branch first.
vra remediate --apply
git log --stat main..vra/remediate   # review what was committed
git push --force origin 'refs/heads/vra/*:refs/heads/vra/*'   # share it yourself

4 vra remediate --open-prDeliver the fixes for review

When do you need it?

When remediation should be a routine code review instead of a project: in CI on a weekly schedule or after every merge, so a fresh, verified fix PR/MR is always waiting for the team — or locally, once you're happy with what --apply produced. It's how security work reaches the people who own the code, in the tool they already use.

What happens, step by step

  1. Everything --apply does — the same isolated, verified, one-fix-at-a-time run.
  2. Finds your provider from the origin remote — GitHub, GitHub Enterprise (github.url), GitLab or self-managed GitLab (gitlab.url) — and a token (Step 1). No token on your machine → GitLab opens the MRs through the push; GitHub gets a one-click link per PR.
  3. Pushes the branches (vra/remediate and vra/needs-human/*, force-pushed because they're regenerated each run) with your own git credentials — SSH or HTTPS.
  4. Opens or updates the PR/MR from vra/remediate into the branch you ran it from, labelled security, vra. The description lists each fix, the CVEs it closes, how it was verified, and what deserves a closer review.
  5. Opens or updates a draft PR/MR for each fix that needs a human — based on the remediation branch, labelled vra:needs-human, with the failure output and what was tried — and links the drafts from the main PR/MR.
  6. Closes drafts that are no longer needed — when a fix that used to fail now passes, its draft is closed with a note.
  7. Opens or updates one secrets issue listing each hardcoded secret by file, line and type (never the value) with revoke → move → purge-history steps.

What you get

  • Links to the PR/MR, drafts and issue in the output
  • The same report files as --apply, plus secrets-<repo>.md
  • Exit code 0 · 2 some fixes need a human (drafts opened) · 1 error

Good to know

  • Idempotent. Re-running updates the same PR/MR, drafts and issue — never duplicates.
  • Tokens: how to create one, which permissions, and what happens without one — Step 1 · Connect.
  • In GitHub Actions, use a personal or app token: PRs opened with the default GITHUB_TOKEN don't trigger your CI.
vra remediate --open-pr
vra remediate --open-pr || [ $? -eq 2 ]   # in CI: "needs a human" isn't a failure

5 vra configCheck the settings VRA+ will use

When do you need it?

Before rolling VRA+ out to a team or pipeline, and whenever a run doesn't behave as expected — “why did it only run one scanner?”, “is CI picking up my environment variables?”. It shows which config file was found and the final value of every setting.

What happens, step by step

  1. Finds the config file — --config, or the first of ./vra.yaml, ./vra.yml, ~/.config/vra+/config.yaml, … (see Configuration).
  2. Merges the sources: defaults, then the file, then VRA__SECTION__KEY environment variables, then global flags — the highest wins.
  3. Masks secrets — tokens and keys show as ***.
  4. Prints the result as tables, or as JSON with --format json.

What you get

  • Every setting with its effective value, by section: scanner, remediation, output, github, gitlab
  • JSON you can pipe into jq or a script

Good to know

  • Changes nothing and needs no network.
  • Safe to paste into a support request — secrets are always masked.
vra config
vra --format json config | jq .scanner.enabled
VRA__SCANNER__SEVERITY_THRESHOLD=MEDIUM vra config   # check an override

CI/CD pipelines

Run VRA+ as two stages. Stage 1 scans and publishes scan-report.json as a pipeline artifact; stage 2 checks out the same commit, downloads the report and opens the fix PR/MR with --report — no re-scan. The scan stage needs no write access.

Stage 1 · scan

checkout → vra scan --no-fail . → publish the report

read-only

scan-report.json
Stage 2 · remediate

checkout the same commit → get the report → vra remediate --open-pr --report …

build toolchain + write token

# .github/workflows/vra.yml
name: VRA+

on:
  schedule:
    - cron: "0 6 * * 1"            # weekly: new CVEs appear against unchanged code
  push:
    branches: [main]               # e.g. after a VRA+ PR is merged
  workflow_dispatch:

env:
  VRA_URL: https://github.com/gboie/vra-plus/releases/latest/download/vra-linux-amd64

jobs:
  # ── Stage 1: scan, and publish the report ──────────────────────────
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: Install VRA+
        run: curl -fsSLo vra "$VRA_URL" && chmod +x vra && sudo mv vra /usr/local/bin/

      - name: Scan
        run: vra scan --no-fail .

      - name: Publish the scan report
        uses: actions/upload-artifact@v4
        with:
          name: vra-scan-report
          path: vra-reports/scan-report.json
          retention-days: 7

  # ── Stage 2: fix what stage 1 found ────────────────────────────────
  remediate:
    needs: scan
    runs-on: ubuntu-latest
    permissions:
      contents: write              # push the vra/* branches
      pull-requests: write         # open / update the PRs
      issues: write                # the secrets issue
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.sha }}   # exactly the commit that was scanned
          fetch-depth: 0
          token: ${{ secrets.VRA_TOKEN }}

      # Your build toolchain, so every fix is verified by your build and tests:
      - uses: actions/setup-node@v4
        with: { node-version: "20" }

      - name: Install VRA+
        run: curl -fsSLo vra "$VRA_URL" && chmod +x vra && sudo mv vra /usr/local/bin/

      - name: Get the scan report from stage 1
        uses: actions/download-artifact@v4
        with:
          name: vra-scan-report
          path: vra-reports

      - name: Remediate and open the PR
        env:
          # A personal or app token: PRs opened with the default GITHUB_TOKEN
          # don't trigger your CI. Needs Contents, Pull requests, Issues and
          # Workflows: Read and write.
          GITHUB_TOKEN: ${{ secrets.VRA_TOKEN }}
        # Exit code 2 = some fixes need a human (draft PRs opened): not a failure.
        run: vra remediate --open-pr --report vra-reports/scan-report.json || [ $? -eq 2 ]
# .gitlab-ci.yml
stages: [scan, remediate]

variables:
  VRA_URL: https://github.com/gboie/vra-plus/releases/latest/download/vra-linux-amd64

.vra:
  image: python:3.12               # an image with your build toolchain
  before_script:
    - curl -fsSLo /usr/local/bin/vra "$VRA_URL" && chmod +x /usr/local/bin/vra
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"           # weekly schedule
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH     # e.g. after a VRA+ MR is merged

# ── Stage 1: scan, and publish the report ────────────────────────────
vra-scan:
  extends: .vra
  stage: scan
  script:
    - vra scan --no-fail .
  artifacts:
    paths: [vra-reports/scan-report.json]
    expire_in: 7 days

# ── Stage 2: fix what stage 1 found ──────────────────────────────────
vra-remediate:
  extends: .vra
  stage: remediate
  needs: [vra-scan]                # same commit; downloads the scan report
  variables:
    GIT_DEPTH: 0                   # full history to branch from
  script:
    # GITLAB_TOKEN: a masked CI/CD variable holding a project access token
    # with the api + write_repository scopes (CI_JOB_TOKEN can't open MRs).
    - git remote set-url origin "https://oauth2:${GITLAB_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.git"
    # Exit code 2 = some fixes need a human (draft MRs opened): not a failure.
    - vra remediate --open-pr --report vra-reports/scan-report.json || [ $? -eq 2 ]
Why the same commit matters

The report describes one commit. Stage 2 must fix that commit, or line numbers and versions won't match. GitLab checks out the pipeline's commit in every job automatically; on GitHub, ref: ${{ github.sha }} does it. Report paths are relative to the scanned folder, so the report works from any checkout.

Detached HEAD

CI checkouts often aren't on a branch. VRA+ then opens the PR/MR against the branch the pipeline runs for — CI_COMMIT_BRANCH on GitLab, GITHUB_REF on GitHub — and stops with a clear message if it can't tell.

Toolchains and Docker in stage 2

Install the tools your build needs (Node, Java, Python, Go…) so every fix is verified by your build and tests. Dockerfile fixes are also checked with docker build — on GitHub runners Docker is already there; on GitLab add services: [docker:dind]. Without a tool, fixes are marked unverified and the PR/MR says so.

Blocking merges on findings

Keep remediation on a schedule and gate pull/merge requests with a separate job that fails on new CRITICAL or HIGH findings:

vra scan --max-critical 0 --max-high 0 .
Tokens

GitHub: a fine-grained token (secret VRA_TOKEN) with Contents, Pull requests, Issues and Workflows: Read and write. PRs opened with the default GITHUB_TOKEN don't trigger your CI. GitLab: a project access token (masked variable GITLAB_TOKEN) with api + write_repository; CI_JOB_TOKEN can't open merge requests.

vra scan

Scan a directory or container image with Trivy, Semgrep and/or Checkov. Findings are grouped by type — SCA, Container, SAST, IaC, Secrets — and a report is always written to vra-reports/scan-report.json, which vra remediate and vra validate read.

When to use it and what happens, step by step: vra scan guide →

vra scan [OPTIONS] TARGET
TARGETpath | imagerequired

What to scan: a directory, a file, or a container image reference. A target that isn't a local path is treated as an image and scanned with Trivy.

vra scan .
vra scan ./services/api
vra scan nginx:1.25
--scanner, -strivy | semgrep | checkov | allall

Which scanner to run. Without the flag, all three run — they're bundled in the binary. Pick one to narrow the scan.

  • trivy — dependencies (SCA), container images, secrets
  • semgrep — source code (SAST)
  • checkov — IaC (Terraform, CloudFormation, ARM, Kubernetes), Dockerfiles, secrets

A container image (any target that isn't a local path) is always scanned with Trivy only — Semgrep and Checkov read files.

Change the default with scanner.enabled in config (VRA__SCANNER__ENABLED=trivy,semgrep).

vra scan .                    # all three
vra scan -s checkov ./infra   # just IaC + secrets
--severityCRITICAL | HIGH | MEDIUM | LOWHIGH

Minimum severity to report. Lower-severity findings are left out of the output and the report.

Config: scanner.severity_threshold · Env: VRA__SCANNER__SEVERITY_THRESHOLD

vra scan --severity MEDIUM .
--fail / --no-failflag--fail

With --fail, the scan exits 1 when the fail policy (the --max-* limits) is breached — use it to gate a pipeline. --no-fail always exits 0 for a reporting-only step; the report is still written.

# Report only — never break the build
vra scan --no-fail .
--max-criticalN0

How many CRITICAL findings are allowed before the scan fails. 0 = any CRITICAL fails; -1 = no limit.

Config: scanner.fail_policy.critical

vra scan --max-critical 0 .
--max-highN0

How many HIGH findings are allowed before the scan fails. 0 = any HIGH fails; -1 = no limit.

Config: scanner.fail_policy.high

# Fail only on CRITICAL; allow any number of HIGH
vra scan --max-critical 0 --max-high -1 .
--max-mediumN-1 (no limit)

How many MEDIUM findings are allowed before the scan fails. Only counts findings at or above --severity.

Config: scanner.fail_policy.medium

vra scan --severity MEDIUM --max-medium 20 .
--max-lowN-1 (no limit)

How many LOW findings are allowed before the scan fails. Only counts findings at or above --severity.

Config: scanner.fail_policy.low

More examples 
# Everything at MEDIUM and above, never fail (typical CI reporting step)
vra scan --severity MEDIUM --no-fail .

# Gate a pipeline: block on any CRITICAL or HIGH
vra scan --max-critical 0 --max-high 0 .

# Scan a built image before pushing it

vra remediate

Fix what vra scan found — dependency upgrades, Semgrep rule fixes, Dockerfile hardening and CI pinning — each verified by your build, tests and a re-scan. Secrets are never patched; they are reported in an issue for rotation. It reads the scan report; it doesn't re-scan the whole project.

Apply fixes on a local branch, vra/remediate, one at a time in an isolated git worktree. Each fix must pass your build, your tests, a docker build of every Dockerfile, and a re-scan — otherwise it's rolled back and kept on a vra/needs-human/<name> branch with the failure output. Your working tree is never touched.

vra remediate --apply
git log --stat main..vra/remediate
--open-prflagoff

Implies --apply. Pushes the branches and opens or updates:

  • one PR/MR with every verified fix,
  • a draft PR/MR per fix that needs a manual change,
  • one issue listing hardcoded secrets to rotate.

Re-running updates them in place — never duplicates. The push uses your own git credentials (SSH works); the token is only used for the GitHub / GitLab API.

Token: GITHUB_TOKEN / GH_TOKEN or GITLAB_TOKEN (also github.token / gitlab.token in config)

GITHUB_TOKEN=… vra remediate --open-pr
GITLAB_TOKEN=… vra remediate --open-pr

Only these fix kinds. Repeat the flag for several.

  • dependency — upgrade vulnerable packages (Maven, Gradle, npm, yarn, pnpm, pip, uv, Poetry, Go)
  • code — apply Semgrep rule fixes

Configuration

Settings come from four places. The highest wins, and only keys that are actually set override lower ones:

CLI flag  >  environment variable  >  vra.yaml  >  default
Config file locations

The first file found is used (or pass --config):

./vra.yaml
./vra.yml
~/.config/vra+/config.yaml
~/.config/vra+/config.yml
~/.vra.yaml
Environment variables

Any key can be set as VRA__<SECTION>__<KEY>. Lists are comma-separated; booleans accept true/false, yes/no, 1/0.

export VRA__SCANNER__ENABLED=trivy,semgrep,checkov
export VRA__SCANNER__SEVERITY_THRESHOLD=MEDIUM
export VRA__OUTPUT__REPORT_DIR=./security-reports
export VRA__REMEDIATION__MAX_CANDIDATES=5
export VRA__GITLAB__URL=https://gitlab.example.com
