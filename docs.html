Quick start

The usual flow: scan, preview the fixes, apply them locally, then open a PR/MR.

# 1. Scan with every bundled scanner (writes vra-reports/scan-report.json)
vra scan --scanner all .

# 2. Preview the fixes — touches nothing
vra remediate

# 3. Apply and verify each fix on a local branch (vra/remediate)
vra remediate --apply

# 4. Push and open the PR/MR, drafts and secrets issue (needs a token)
GITHUB_TOKEN=… vra remediate --open-pr

Global options

Global options go before the command: vra --format json scan .

vra [GLOBAL OPTIONS] COMMAND [OPTIONS] [ARGS]
--config, -cPATHauto-discovered

Path to a vra.yaml config file. Overrides the auto-discovery order.

Env var: VRA_CONFIG_FILE

vra --config ./team-config.yaml scan --scanner all ./myservice
--format, -frich | json | sarifrich

Output format on stdout. rich is the colour terminal report; json and sarif are machine-readable (SARIF uploads to code-scanning dashboards). The report file is written either way.

Env var: VRA_OUTPUT_FORMAT

vra --format json scan . > findings.json
vra --format sarif scan --scanner all . > vra.sarif
--verbose, -vflagoff

Enable verbose output. Same as output.verbose: true in config.

vra -v scan --scanner semgrep .
--versionflag

Print the VRA+ version and exit.

vra --version
--install-completionflag

Install tab completion for your current shell (bash, zsh, fish, PowerShell). Restart the shell afterwards.

vra --install-completion
--show-completionflag

Print the completion script instead of installing it — to copy it or customise the installation.

--helpflag

Show help. Works on every command: vra scan --help, vra remediate --help…

vra scan

Scan a directory or container image with Trivy, Semgrep and/or Checkov. Findings are grouped by type — SCA, Container, SAST, IaC, Secrets — and a report is always written to vra-reports/scan-report.json, which vra remediate and vra validate read.

vra scan [OPTIONS] TARGET
TARGETpath | imagerequired

What to scan: a directory, a file, or a container image reference. Trivy detects image vs filesystem automatically.

vra scan .
vra scan ./services/api
vra scan nginx:1.25
--scanner, -strivy | semgrep | checkov | alltrivy

Which scanner to run. all runs the three together.

  • trivy — dependencies (SCA), container images, secrets
  • semgrep — source code (SAST)
  • checkov — IaC, Dockerfiles, CI configs, secrets

Default comes from scanner.enabled in config (VRA__SCANNER__ENABLED).

vra scan --scanner all .
vra scan -s checkov ./infra
--severityCRITICAL | HIGH | MEDIUM | LOWHIGH

Minimum severity to report. Lower-severity findings are left out of the output and the report.

Config: scanner.severity_threshold · Env: VRA__SCANNER__SEVERITY_THRESHOLD

vra scan --scanner all --severity MEDIUM .
--fail / --no-failflag--fail

With --fail, the scan exits 1 when the fail policy (the --max-* limits) is breached — use it to gate a pipeline. --no-fail always exits 0 for a reporting-only step; the report is still written.

# Report only — never break the build
vra scan --scanner all --no-fail .
--max-criticalN0

How many CRITICAL findings are allowed before the scan fails. 0 = any CRITICAL fails; -1 = no limit.

Config: scanner.fail_policy.critical

vra scan --scanner all --max-critical 0 .
--max-highN0

How many HIGH findings are allowed before the scan fails. 0 = any HIGH fails; -1 = no limit.

Config: scanner.fail_policy.high

# Fail only on CRITICAL; allow any number of HIGH
vra scan --scanner all --max-critical 0 --max-high -1 .
--max-mediumN-1 (no limit)

How many MEDIUM findings are allowed before the scan fails. Only counts findings at or above --severity.

Config: scanner.fail_policy.medium

vra scan --severity MEDIUM --max-medium 20 .
--max-lowN-1 (no limit)

How many LOW findings are allowed before the scan fails. Only counts findings at or above --severity.

Config: scanner.fail_policy.low

More examples 
# Everything at MEDIUM and above, never fail (typical CI reporting step)
vra scan --scanner all --severity MEDIUM --no-fail .

# Gate a pipeline: block on any CRITICAL or HIGH
vra scan --scanner all --max-critical 0 --max-high 0 .

# Scan a built image before pushing it
vra scan --scanner trivy registry.example.com/app:1.4.2

# Only IaC and secrets
vra scan --scanner checkov --severity MEDIUM .

# SARIF for a code-scanning dashboard
vra --format sarif scan --scanner all . > vra.sarif

vra remediate

Fix what vra scan found — dependency upgrades, Semgrep rule fixes, Dockerfile hardening and CI pinning — each verified by your build, tests and a re-scan. Secrets are never patched; they are reported in an issue for rotation. It reads the scan report; it doesn't re-scan the whole project.

vra remediate [OPTIONS]
vra remediate

Plan. Shows and saves what would change. Touches nothing.

--apply

Apply. Verified fixes committed on a local branch.

--open-pr

Deliver. Push, open the PR/MR, drafts and secrets issue.

--report, -rPATHvra-reports/scan-report.json

The scan report to fix. Defaults to scan-report.json in the report directory (output.report_dir).

vra remediate --report ./artifacts/scan-report.json
--applyflagoff

Apply fixes on a local branch, vra/remediate, one at a time in an isolated git worktree. Each fix must pass your build, your tests, a docker build of every Dockerfile, and a re-scan — otherwise it's rolled back and kept on a vra/needs-human/<name> branch with the failure output. Your working tree is never touched.

vra remediate --apply
git log --stat main..vra/remediate
--open-prflagoff

Implies --apply. Pushes the branches and opens or updates:

  • one PR/MR with every verified fix,
  • a draft PR/MR per fix that needs a manual change,
  • one issue listing hardcoded secrets to rotate.

Re-running updates them in place — never duplicates. The push uses your own git credentials (SSH works); the token is only used for the GitHub / GitLab API.

Token: GITHUB_TOKEN / GH_TOKEN or GITLAB_TOKEN (also github.token / gitlab.token in config)

GITHUB_TOKEN=… vra remediate --open-pr
GITLAB_TOKEN=… vra remediate --open-pr
--kinddependency | code | dockerfile | workflowall

Only these fix kinds. Repeat the flag for several.

  • dependency — upgrade vulnerable packages (Maven, Gradle, npm, yarn, pnpm, pip, uv, Poetry, Go)
  • code — apply Semgrep rule fixes
  • dockerfile — non-root user, digest-pinned base image, COPY not ADD, no port 22, apt-get update merged, MAINTAINER → LABEL
  • workflow — pin CI actions to commit SHAs

Config: remediation.kinds

vra remediate --apply --kind dockerfile --kind code
--onlyNAMEall

Limit to these packages or rules. Repeat the flag for several.

vra remediate --apply --only log4j-core
vra remediate --apply --only requests --only urllib3
--max-candidatesN3

How many fixing versions to try per package before handing it to a human. VRA+ starts from the lowest version that closes every CVE and moves up when the build fails.

Config: remediation.max_candidates

vra remediate --apply --max-candidates 5
--verify-commandCMDauto-detected

Build/test command to run instead of the detected one. Runs through your shell (sh, or cmd.exe on Windows).

DetectedVerification
pom.xmlmvnw verify / mvn verify
build.gradle(.kts)gradlew build / gradle build
package.jsoninstall, then run build and run test if defined (npm, yarn or pnpm)
uv.lockuv sync · uv pip check · pytest
poetry.lockpoetry install · pip check · pytest
requirements.txtthrowaway venv · pip check · pytest (or byte-compile)
go.modgo mod tidy · go build · go test
Dockerfile*docker build

Config: remediation.verify_command

vra remediate --apply --verify-command "./mvnw -B -q -DskipITs verify"
vra remediate --apply --verify-command "make ci"
--skip-verifyflagoff

Don't build or test. Every fix is marked unverified, and the PR/MR says so — let your CI decide.

Config: remediation.skip_verify

vra remediate --open-pr --skip-verify
What access you need
You havePlan--apply--open-pr
A clone (even read-only)✅✅ local commits—
+ push access (SSH or HTTPS)✅✅ then push yourself—

Without a token, push the branches and open the PR/MR yourself:

vra remediate --apply
git push --force origin 'refs/heads/vra/*:refs/heads/vra/*'

Token permissions. With an SSH remote (push via your key): GitHub Pull requests + Issues read/write, or GitLab api. In CI, where the token also pushes: add Contents + Workflows (GitHub) or write_repository (GitLab).

More examples 
# See what would change
vra remediate

# Only dependency upgrades, verified locally
vra remediate --apply --kind dependency

# Only the Log4Shell fix, with a custom build
vra remediate --apply --only log4j-core --verify-command "./mvnw -B -q verify"

# CI: open the PR/MR; exit code 2 (needs a human) isn't a failure
vra remediate --open-pr || [ $? -eq 2 ]

Written to the report directory: remediation-plan.json, remediation-report.json and pr-<repo>.md (the PR description).

vra validate preview

Re-scan a target and compare it with the original report to confirm the fixes closed the findings. Today it loads the original report and shows the baseline counts; full re-scan diffing is in progress.

vra validate [OPTIONS]
--report, -rPATHvra-reports/scan-report.json

The original scan report to compare against.

vra validate --report ./vra-reports/scan-report.json

vra config

Print the effective configuration after merging the config file, environment variables and defaults. Tokens and keys are always shown as ***, so it's safe to share.

vra config
vra --format json config
vra --config ./team-config.yaml config

Configuration

Settings come from four places. The highest wins, and only keys that are actually set override lower ones:

CLI flag  >  environment variable  >  vra.yaml  >  default
Config file locations

The first file found is used (or pass --config):

./vra.yaml
./vra.yml
~/.config/vra+/config.yaml
~/.config/vra+/config.yml
~/.vra.yaml
Environment variables

Any key can be set as VRA__<SECTION>__<KEY>. Lists are comma-separated; booleans accept true/false, yes/no, 1/0.

export VRA__SCANNER__ENABLED=trivy,semgrep,checkov
export VRA__SCANNER__SEVERITY_THRESHOLD=MEDIUM
export VRA__OUTPUT__REPORT_DIR=./security-reports
export VRA__REMEDIATION__MAX_CANDIDATES=5
export VRA__GITLAB__URL=https://gitlab.example.com
Example vra.yaml 
scanner:
  enabled: [trivy, semgrep, checkov]
  severity_threshold: HIGH
  timeout_seconds: 300
  fail_policy: { critical: 0, high: 0, medium: -1, low: -1 }

remediation:
  kinds: [dependency, code, dockerfile, workflow]
  max_candidates: 3
  verify_timeout_seconds: 900
  labels: [security, vra]

output:
  format: rich
  report_dir: ./vra-reports

gitlab:
  url: https://gitlab.example.com   # self-managed GitLab
